# Conducto A2A 1.0 profile

Conducto Milestone 4 pins the A2A wire contract to the released A2A
specification `1.0.0`, using JSON-RPC as the only network binding in scope.
The Conducto package version is independent from this protocol version.

## Normative source and generated artifacts

| Item | Value |
|---|---|
| A2A release | `v1.0.0` / protocol release `1.0.0` |
| Runtime protocol version | `1.0` in `supportedInterfaces[].protocolVersion` |
| Normative source | `https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto` |
| Normative commit | `173695755607e884aa9acf8ce4feed90e32727a1` |
| `a2a.proto` SHA-256 | `4b74c0baa923ae0acb55474e548f1d6e5d3f83b80d757b65f8bf3e99a3c2257f` |
| Official Python SDK | `a2a-sdk==1.0.3` |
| License/provenance | Upstream A2A and `a2a-sdk` are Apache-2.0 licensed |

The upstream `a2a.proto` for `v1.0.0` is normative. Conducto does not edit
generated SDK types by hand. Python validation parses Agent Cards, messages,
and tasks through the pinned official SDK, while language-neutral fixtures in
`tests/golden/fixtures/a2a/a2a_1_0_conformance.json` preserves the
observable wire behavior later SDKs must match.

To verify the pinned source artifact:

```bash
curl -fsSL \
  https://raw.githubusercontent.com/a2aproject/A2A/v1.0.0/specification/a2a.proto \
  -o /tmp/a2a.proto
sha256sum /tmp/a2a.proto
```

The SHA-256 output must equal the value in the table above. Re-running fixture
generation is done by invoking the checked-in Python Agent Card generator and
then running the golden suite:

```bash

uv run python - <<'PY'
from pathlib import Path
from tests.golden.test_agent_card_golden import GoldenAgent

Path("tests/golden/fixtures/golden_agent_card.json").write_text(
    GoldenAgent().get_agent_card_json("https://golden.conducto.test/a2a") + "\n",
    encoding="utf-8",
)
PY
uv run pytest tests/golden
git diff --check
```

## Feature and operation matrix

| A2A feature or operation | Conducto Milestone 4 profile |
|---|---|
| Agent Card retrieval | Supported for public cards generated by `BaseAgent.get_agent_card()` |
| Extended authenticated Agent Card retrieval | Deferred; cards advertise `extendedAgentCard: false` |
| `message/send` | Supported by profile fixtures; Conducto always returns a `Task` outcome |
| Direct message responses | Not supported; follow-up work creates or updates tasks |
| `message/stream` | Deferred and rejected as an unsupported operation |
| `tasks/get` | Supported by profile fixtures |
| `tasks/list` | Supported by profile fixtures |
| `tasks/cancel` | Supported by profile fixtures |
| Push notification configuration | Deferred; cards advertise `pushNotifications: false` |
| Non-text modalities | Deferred; only `text/plain` is accepted |
| Required unknown Agent Card extensions | Rejected explicitly |
| Legacy A2A 0.3 Agent Cards | Rejected explicitly; no compatibility adapter is maintained |

## Agent Card mapping

Conducto maps reflected Python agents into A2A 1.0 fields:

- agent identity maps to `name`, `description`, and `version`
- the advertised endpoint maps to one `supportedInterfaces` entry with
  `protocolBinding: "JSONRPC"` and `protocolVersion: "1.0"`
- capabilities map to `skills[]` with deterministic `conducto-<sha256...>`
  skill IDs
- `defaultInputModes`, `defaultOutputModes`, and skill modes are
  `["text/plain"]`
- OpenAPI-style security inputs are adapted into A2A 1.0
  `securitySchemes` and `securityRequirements`
- reflected parameter schemas live under the optional
  `https://conducto.ai/a2a/extensions/parameters/v1` extension as
  `params.x-conducto.parameters`, keyed by A2A skill ID

The `x-conducto` data is extension payload data, not a top-level Agent Card
field, so it does not collide with standard A2A fields.

## Messages, tasks, artifacts, and identifiers

Conducto uses official A2A SDK message and task field names. Callers own
request, correlation, and idempotency identifiers. The local runtime owns task
IDs, context IDs, message IDs, and artifact IDs when it constructs A2A
responses for local capability execution.

Task states use the A2A 1.0 `TaskState` enum. Terminal states are immutable:
`TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, and
`TASK_STATE_REJECTED` cannot transition to another state. A follow-up request
after a terminal task creates a new task in the same context rather than
resuming the terminal task.

`InvocationResult` variants are mapped to protocol outcomes without exposing
Python or .NET exception objects:

| Conducto result | A2A outcome |
|---|---|
| `InvocationSuccess` | completed task with result artifacts or final message data |
| `InvocationValidationFailure` | JSON-RPC invalid-params error |
| `InvocationTargetNotFound` | task/capability not found error |
| `InvocationTimeout` | failed task with timeout metadata |
| `InvocationCancelled` | canceled task |
| authorization, approval, audit, binding, budget, delegation failures | typed failed task or JSON-RPC error according to request phase |
| unexpected `InvocationFailure` | internal error with sanitized message |

## Limits used by conformance tests

| Limit | Value |
|---|---|
| Message parts | `16` |
| Metadata size | `4096` UTF-8 bytes after canonical JSON encoding |
| Task history messages | `32` |
| Task artifacts | `16` |
| Artifact parts | `16` |
| Supported media types | `text/plain` |

Positive and negative boundary examples are checked in under
`tests/golden/fixtures/a2a/`. The fixtures intentionally use example
hosts under `.test` and contain no credentials, tokens, private keys, prompts,
or production endpoints.

## Compatibility and update procedure

A2A 0.3 clients receive explicit unsupported-version failures because Conducto
does not maintain a 0.3 compatibility adapter. Do not mix 0.3 and 1.0 fields in
one wire object.

To evaluate a later A2A patch or major version:

1. Review the upstream release notes and `a2a.proto` diff.
2. Update the pinned provenance constants and `a2a-sdk` dependency only if the
   official SDK supports the target specification.
3. Regenerate the golden Agent Card fixture and update language-neutral
   conformance fixtures for intentional wire changes.
4. Document compatibility impact, especially removed fields, new required
   fields, operation support, extension behavior, and media-type changes.
5. Run the golden, focused protocol tests, and the full Python validation gate
   from the repository root.
